# 小张的餐厅 · 精简方案设计

> 版本 v0.3（评审稿） · 2026-11-07
> 本文覆盖 v0.1《方案设计》，冲突之处以本文为准。只写方案，不写业务代码。

**本轮精简的边界**

- 不做支付、价格、金额、成本；菜单只呈现名称、图片、简介、分类。
- 不做库存、不做扣减、不做用量与单位；配方只记录"这道菜需要哪些食材"。
- 订单只有三种状态：待处理、制作中、完成。
- 权限改为超级用户授权制，不再使用环境变量 + openid 白名单。
- 单店、单机、SQLite 单文件；不做自动备份与运维体系。
- AI 推荐菜品、中英文切换本期不实现，只保留设计与字段位置。

## 1. 技术选型与部署

| 层 | 选择 | 理由 |
|---|---|---|
| 小程序 | 原生小程序 + TypeScript + TDesign | 只发微信端，无跨端诉求；原生对自定义 tabBar、分包、i18n 控制最直接 |
| 后端 | Node.js 24 LTS + Fastify + TypeScript | 接口少、单进程，Fastify 启动快、插件与校验够用 |
| 数据库 | SQLite + better-sqlite3（WAL） | 单文件、零运维，单店数据量完全够用；同步驱动写代码最简单 |
| 数据访问 | 预编译 SQL + 编号迁移 | 表只有 10 张，不引入 ORM/Kysely，减少一层学习与调试成本 |
| 图片 | 服务器本地磁盘 `/data/uploads` + Caddy 静态服务 | 单机单店，省掉对象存储、密钥与额外域名 |
| 部署 | 1 台轻量云服务器 + Docker Compose（Caddy + API） | SQLite 需要持久本地盘；单实例足够，多实例写同一库不可行 |

```
小程序 ──HTTPS──> Caddy ──> Fastify ──> SQLite（/data/restaurant.db）
                              └──────> 图片（/data/uploads，Caddy 直出）
```

- SQLite 开 WAL、单进程单实例写，避免 `SQLITE_BUSY` 与多写冲突。
- SQLite 是单文件，备份按需自行拷贝即可，本方案不展开运维与备份。
- 不使用 WebSocket：商家看板 30s 轮询 + 下拉刷新足够。

## 2. 身份、权限与登录持久化

### 2.1 登录与"下次还能看到订单"

1. 小程序 `wx.login` 拿 `code`，服务端 `code2session` 换 `openid`。
2. 按 `openid` upsert `app_user`，签发 JWT（只含 `uid`，有效期 30 天）。
3. 客户端把 `token` 与 `userId` 写入 `wx.setStorage`；启动时先静默登录，token 失效则自动重登。
4. 订单归属由服务端 `orders.customer_id` 决定，不依赖本地存储。即使换手机、清缓存，只要还是同一微信 `openid`，就会映射到同一条 `app_user`，历史订单仍在。
5. 客户端传的 `userId` 一律不采信，服务端只从 JWT 取当前用户。

### 2.2 三种视角与权限

| 能力 | 客户 | 商家（被授权） | 超级用户 |
|---|---|---|---|
| 看菜单、下单、查看本人订单 | ✓ | ✓ | ✓ |
| 查看全部订单、推进状态、看采购 | ✗ | ✓ | ✓ |
| 维护分类、菜品、食材 | ✗ | ✓ | ✓ |
| 授权/撤销商家端访问 | ✗ | ✗ | ✓ |

- 每个登录用户天然拥有客户视角；`can_merchant=1` 增加商家视角；`is_super=1` 增加超级用户视角，并隐含商家权限。
- 入口页列出当前可用视角；只有客户一个视角时直接进菜单，多视角时选择并记 `last_role`。
- 切换视角不换账号：同一个 `app_user`，只是换页面与接口权限。

### 2.3 超级用户与商家授权如何落库

- `app_user.is_super`：超级用户标识，只能由初始化逻辑写入，没有任何接口可以授予/转让。
- `app_user.can_merchant`：商家端访问开关。
- `app_user.merchant_granted_by`、`merchant_granted_at`：记录最近一次授权人与时间；撤销时把 `can_merchant` 置 0，保留这两个字段备查。
- 初始化：库中还没有超级用户时，第一个成功登录的用户自动置 `is_super=1`，之后不再触发。
- 超级用户在"用户授权"页从 `app_user` 列表（即所有登录过的用户）里选择对象，调用授权接口开启/关闭商家端权限。
- 鉴权中间件每次请求都从数据库读取 `is_super` / `can_merchant`，不把角色写进 JWT；撤销权限立即生效，不用等 token 过期。

### 2.4 客户订单隔离

- `orders.customer_id` 非空，是唯一隔离键。
- 客户接口强制 `WHERE customer_id = 当前 uid`；订单详情再校验归属，不匹配返回 404。
- 商家接口不按用户过滤（只按日期/状态筛选），返回全部用户订单。
- 超级用户通过商家接口看全部订单；它自己的客户订单仍走客户接口，只看到自己的。

## 3. 订单：三状态与取消

完整流程：**进入小程序 → 选择角色（单视角直接进入）→ 点餐下单 → 待处理 → 制作中 → 完成**。中间没有取餐、核销、叫号等环节。

### 3.1 状态机

| 状态 | 含义 | 进入方式 | 可执行动作 |
|---|---|---|---|
| `pending` | 待处理 | 客户提交订单 | 商家"开始制作"；客户或商家取消 |
| `cooking` | 制作中 | 商家点"开始制作" | 商家点"完成" |
| `completed` | 完成 | 商家点"完成" | 客户评价 |

- 只允许 `pending → cooking → completed` 单向推进，不设回退。
- `orders.cooking_at`、`completed_at` 记录推进时间；订单详情按"下单 → 开始制作 → 完成"展示时间线。
- 不做逐菜状态：整单只有一个进度，减少后厨操作与前端状态。

### 3.2 取消怎么表达（建议）

**不新增第四种状态，取消 = 软删除。** `orders.deleted_at` + `deleted_by_user_id` 记录，订单状态仍是 `pending`。

- 客户只能取消自己的 `pending` 订单；商家可以取消任意 `pending` 订单。
- `cooking` 之后不允许系统内取消：后厨已开工、采购已生成，直接在系统里抹掉会让两侧口径不一致；单店线下沟通处理。
- `completed` 不可取消。
- 被取消订单从客户列表、商家看板、日历、采购聚合中全部排除，详情返回 404。

选择软删除而不是物理删除：单店数据量小，误点可恢复，也保留"谁在什么时候取消"的痕迹。选择不加 `cancelled` 状态：三状态是明确约束，取消用独立删除标记表达，列表与统计只需统一加 `deleted_at IS NULL`。

### 3.3 进度查看

- 客户订单详情在 `onShow` 与 30s 轮询时刷新，看到"待处理/制作中/完成"与对应时间。
- 商家看板按三列展示，卡片上直接提供"开始制作/完成"。
- 通知商家：看板轮询未处理单 + 新单提示音；离店提醒可后续加微信订阅消息，v1 不阻塞主流程。

## 4. 采购详情

- 配方表 `dish_ingredient` 只记录"菜品 ↔ 食材"的对应关系，没有数量、单位、损耗。
- 下单事务内：取本次所有菜品的 `dish_ingredient`，按 `ingredient_id` 去重，为每个食材写一条 `order_ingredient` 快照（含食材中文名，英文字段预留）。
- 同一道菜出现多份、同一食材被多道菜使用，最终都只算一条，不做数量换算。
- 商家采购页按 `business_date` 聚合：列出当天所有未删除订单涉及的食材，去重展示，并标注"被 N 个订单需要"；不提供勾选、库存、成本。
- 订单取消后，快照数据保留，但通过 `orders.deleted_at` 在聚合时排除。
- 菜品没有配配方时不产生采购行；菜品编辑页必须提示"未配置食材，不会进入采购清单"。

## 5. 评价、日历、图片与预留项

### 5.1 评分与评论

- 一单一条评价：`review.order_id` 唯一；仅 `completed` 订单可评，重复提交返回 `REVIEW_DUPLICATED`。
- 整单星级必填；每个菜品可单独 1–5 星，并可选填短评。
- 客户不能修改/删除；商家只能隐藏内容（`is_hidden`），不能改分数。
- 菜品详情展示未隐藏评价的均分与条数，查询时聚合，不做缓存。

### 5.2 日历

- 下单时按 `Asia/Shanghai` 落 `orders.business_date`，查询不再做时区换算。
- 客户日历只统计本人订单：月视图返回每天订单数；点某天展开当天的订单与菜品，回答"那天吃了什么"。
- 已取消（软删除）订单不计入；`business_date` 建索引。
- 商家不需要日历，订单看板按日期筛选即可。

### 5.3 图片

- 客户端 `wx.chooseMedia` → `wx.compressImage` → `wx.uploadFile`；服务端校验类型与大小（≤5MB），随机文件名写入 `/data/uploads/yyyy/mm/`。
- 数据库只存 `image_key`（相对路径），展示时拼域名；Caddy 直接托管 `/uploads`。
- 绝不把 `wxfile://tmp_xxx` 临时路径入库；上传接口只开放给商家。
- 换图只改 key，旧文件可手工清理，不做自动对账与删除任务。

### 5.4 本期不实现的预留项

- **中英文切换**：本期界面与接口全部中文。`app_user.locale`、分类/菜品/食材的 `name_en`、菜品的 `intro_en` 只作为预留字段存在，不写入、不展示、不提供切换入口。将来的改动见 `docs/架构与数据模型.md` 的"预留设计"。
- **AI 推荐菜品**：本期不建推荐表、不做推荐接口、不在菜单页放置推荐位。将来以独立表 + 独立接口 + 菜单页横向卡片的形式追加，不改现有订单、菜品与权限结构。


## 6. 数据模型

### 6.1 关系

```
app_user 1─n orders 1─n order_item n─1 dish n─1 dish_category
dish n─n ingredient（通过 dish_ingredient）
orders 1─n order_ingredient n─1 ingredient
orders 1─1 review 1─n review_item n─1 dish
```

### 6.2 表清单与关键字段

> 这里是关键字段摘要；字段级类型、默认值、可空、索引与完整 DDL 见 `docs/架构与数据模型.md`。

| 表 | 作用 | 关键字段 | 约束/索引 |
|---|---|---|---|
| `app_user` | 登录用户、权限 | id, openid, nickname, is_super, can_merchant, merchant_granted_by, merchant_granted_at, last_role, locale, created_at, last_login_at | `UNIQUE(openid)` |
| `dish_category` | 菜品分类 | id, name_zh, name_en, sort_order, is_active | |
| `dish` | 菜品 | id, category_id, name_zh, name_en, intro_zh, intro_en, image_key, is_available, sort_order | 索引 `(category_id, sort_order)` |
| `ingredient` | 食材库 | id, name_zh, name_en, is_active | |
| `dish_ingredient` | 菜品所需食材（无用量） | dish_id, ingredient_id | 主键 `(dish_id, ingredient_id)` |
| `orders` | 订单 | id, customer_id, status, remark, business_date, created_at, cooking_at, completed_at, deleted_at, deleted_by_user_id | `status CHECK(pending/cooking/completed)`；索引 `(customer_id, created_at)`、`(business_date, status)`、`(status, created_at)` |
| `order_item` | 订单明细 | id, order_id, dish_id, name_zh, name_en, qty | 索引 `(order_id)` |
| `order_ingredient` | 采购快照 | id, order_id, ingredient_id, name_zh, name_en | `UNIQUE(order_id, ingredient_id)`；索引 `(ingredient_id)` |
| `review` | 整单评价 | id, order_id, customer_id, rating, content, is_hidden, created_at | `UNIQUE(order_id)` |
| `review_item` | 菜品评价 | id, review_id, dish_id, rating, content | `UNIQUE(review_id, dish_id)`；索引 `(dish_id)` |

### 6.3 落库说明

- **订单隔离**：`orders.customer_id` 关联 `app_user.id`；所有客户查询由服务端注入当前 uid，详情二次校验，客户端无法通过参数越权。
- **商家授权**：权限落在 `app_user.can_merchant`，`merchant_granted_by/at` 记录授权来源；授权接口只允许 `is_super=1` 调用，每次请求现查数据库。
- **超管来源**：`app_user.is_super` 由"首个登录用户"初始化，不提供任何写入接口。
- **历史稳定**：`order_item` 存菜名快照，`order_ingredient` 存食材名快照，菜品改名或删除不影响历史订单与采购记录；字典统一软删（`is_active` / `is_available`）。
- 取消订单不物理删除，靠 `orders.deleted_at` 过滤；评价只允许完成订单，因此不会出现"订单没了、评价还在"。
- `orders.remark` 只用于口味/特殊要求备注，与取餐无关。
- **预留字段**：`app_user.locale`、`name_en`、`intro_en` 为将来的中英文切换保留，本期不读写；AI 推荐不在现有表中加字段，将来用独立表与独立接口追加。
- 无金额字段、无价格字段、无库存字段；数据库不存任何支付信息。

## 7. 接口清单

统一前缀 `/api/v1`，`Authorization: Bearer <jwt>`；成功 `{ ok: true, data }`，失败 `{ ok: false, code, params }`。列表统一 `page/pageSize`。

**公共与客户**

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/wx-login` | `{code}` → token、userId、isSuper、canMerchant、lastRole |
| GET | `/me` | 当前用户与可用视角 |
| PATCH | `/me` | `{lastRole?, nickname?}` |
| GET | `/categories` | 启用中的分类 |
| GET | `/dishes?categoryId=` | 菜单：名称、图片、简介、分类 |
| GET | `/dishes/:id` | 详情 + 评分均分/条数 |
| GET | `/dishes/:id/reviews` | 未隐藏的菜品评价 |
| POST | `/orders` | `{items:[{dishId, qty}], remark}`，只收菜品与数量 |
| GET | `/orders?status=&page=` | **仅本人订单**，按当前 uid 过滤 |
| GET | `/orders/:id` | 本人订单详情；非本人返回 404 |
| DELETE | `/orders/:id` | 本人 `pending` 订单软删除；其他状态返回 `ORDER_NOT_DELETABLE` |
| POST | `/orders/:id/review` | 本人 `completed` 订单评价，一单一评 |
| GET | `/orders/:id/review` | 本人评价 |
| GET | `/calendar?month=YYYY-MM` | 本人日历月聚合 |
| GET | `/calendar/YYYY-MM-DD` | 本人某日订单与菜品 |

**商家（`can_merchant=1` 或 `is_super=1`）**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/merchant/orders?date=&status=&page=` | **全部用户订单**，不按用户过滤 |
| GET | `/merchant/orders/:id` | 订单详情、状态时间线 |
| POST | `/merchant/orders/:id/start` | `pending → cooking` |
| POST | `/merchant/orders/:id/complete` | `cooking → completed` |
| DELETE | `/merchant/orders/:id` | 任意 `pending` 订单软删除 |
| GET | `/merchant/purchases?date=` | 按日聚合的食材清单（去重、无数量） |
| GET | `/merchant/categories` | 含停用分类 |
| POST / PATCH | `/merchant/categories`、`/merchant/categories/:id` | 新增/改名/排序/启停 |
| GET | `/merchant/dishes` | 含下架菜品 |
| POST / PATCH | `/merchant/dishes`、`/merchant/dishes/:id` | 菜品字段 + `ingredientIds[]`，无价格 |
| POST | `/merchant/uploads/image` | multipart，返回 `image_key` |
| GET | `/merchant/ingredients` | 食材库 |
| POST / PATCH | `/merchant/ingredients`、`/merchant/ingredients/:id` | 新增/改名/启停 |
| PATCH | `/merchant/reviews/:id` | `{hidden:true/false}`，只隐藏内容 |

**超级用户（`is_super=1`）**

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/users?keyword=&page=` | 所有登录过的用户：昵称、openid（脱敏）、can_merchant、last_login_at |
| PATCH | `/admin/users/:id/merchant-access` | `{allowed:true/false}`，授权/撤销商家端 |

**错误码（节选）**：`AUTH_REQUIRED`、`ROLE_FORBIDDEN`、`ORDER_NOT_FOUND`、`ORDER_STATE_INVALID`、`ORDER_NOT_DELETABLE`、`REVIEW_DUPLICATED`、`UPLOAD_INVALID`、`DISH_UNAVAILABLE`。

## 8. 页面结构

用**自定义 tabBar** 按视角渲染；入口页负责视角选择，之后只展示该视角的 tab。

| 页面 | 路由 | 入口 | 内容 |
|---|---|---|---|

## 9. 仍待确认

**1. 服务器与备案域名是否就绪？**
