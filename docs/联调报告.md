### 3.2 额外发现并修复的契约问题

这些问题不在原 18 条清单里，但会直接导致页面行为错误：

1. **`PATCH /me` 回包缺少 `isSuper/canMerchant`**：前端在切换视角时会把回包整体覆盖全局用户，导致超管切到商家端后被守卫判定为无权限。现改为返回与 `GET /me` 相同的完整用户对象，并补 `openidMasked`、`lastLoginAt`。
2. **`GET /dishes/:id/reviews` 缺 `id`**：小程序以 `id` 作为列表 key，原返回只有 `reviewId`。现补充 `id`。
3. **评价详情缺菜名**：`GET /orders/:id/review` 的 `items[]` 没有 `nameZh`，评价页直接渲染会出现空白菜名。现通过关联 `dish` 补齐。
4. **订单缺 `reviewed`**：`/orders`、`/merchant/orders` 与 `/calendar/:date` 不一致。现统一在订单序列化中输出 `reviewed`。
5. **mock 登录每次新建用户**：开发者工具的 `wx.login` code 每次都变，原逻辑按 code 派生 openid，会不断创建新用户，“首个用户即超管”只在第一次成立。现改为：普通 code 固定映射 `mock_dev`；显式 `mock_xxx` 才生成独立测试用户（脚本联调仍可用）。
6. **菜品列表评分不显示**：后端在菜品对象里返回 `rating:{avg,count}`，前端只读扁平 `ratingAvg`。现 `normalizeDish` 兼容嵌套 `rating`；菜单/菜品页可显示评分。
7. **商家订单客户 id 丢失**：前端读扁平 `customerId`，后端只给 `customer` 对象。除第 12 条后端补字段外，前端也兼容 `customer.id` 作为兜底。
8. **openid 二次脱敏**：后端已返回 `mock_1****abcd`，前端再次截断会变成 `mock…abcd`。现 `maskOpenid` 识别已脱敏文本直接展示。

## 6. 仍存在的不一致 / 未覆盖点

1. **无 `GET /merchant/dishes/:id`**：编辑页依赖列表按 id 查找，且列表默认一页 50 条、没有加载更多；菜品超过 50 道时，排在后面的菜品可能无法进入编辑。当前演示 6 道无影响；后续菜品规模上来，建议加单条详情或分页。
2. **列表固定 `pageSize=50`**：客户订单、商家订单、超管用户均只取第一页，没有滚动加载；超过 50 条时旧数据不可见。当前演示数据量无影响。
3. **真实微信登录未验证**：本机无 `WECHAT_APPID/SECRET`，只验证了 mock 登录；上线前需配置环境变量，并用真机确认 `jscode2session`。
4. **上传格式只实测 PNG**：JPEG/WebP/GIF 由后端 MIME 白名单支持，但未逐一构造文件验证。
5. **上传文件无回收机制**：替换菜品图片后旧文件不会自动删除，也没有删除接口；不影响演示与功能范围。
6. **评价隐藏无前端入口**：后端支持 `PATCH /merchant/reviews/:id`，本期小程序未提供该操作，不属于本次范围。
7. **采购清单不含量与单位**：按设计只做食材聚合与订单号/菜名提示。

## 8. Windows 中文日志乱码修复（2026-11-11）

### 8.1 现象

在 Windows PowerShell 里直接 `npm run dev`，服务能正常启动，但启动提示显示为乱码：

```
{"level":40,...,"msg":"寰俊鐧诲綍澶勪簬 mock 妯″紡锛氬紑鍙戣€呭伐鍏� code ..."}
{"level":40,...,"msg":"JWT_SECRET 浠嶄负榛樿鍊硷紝涓婄嚎鍓嶈瀵版崲"}
```

### 8.2 根因

- Node 的 stdout/stderr 始终按 UTF-8 输出字节；日志内容是正确的中文。
- 简体中文 Windows 控制台默认代码页是 936（GBK）。`npm run dev` 在 Windows 下由 cmd 执行，npm 会把子进程输出转发到同一个控制台，控制台用当前代码页（936）去解码 UTF-8 字节，于是中文变成「寰俊鐧诲綍…」这种典型乱码。
- 结论：不是编码写错，而是**控制台解码方式**与输出编码不一致。

### 8.3 修改内容

新增 [console-utf8.ts](file:///c:/projectCode/zhang-restaurant/server/src/lib/console-utf8.ts)，提供 `ensureUtf8Console()`：在 Windows 上于进程启动最早期执行一次 `cmd /d /c chcp 65001`，把**当前控制台**切到 UTF-8；非 Windows 直接返回，切换失败静默降级。

调用点（均在输出任何中文之前）：

| 文件 | 说明 |
| --- | --- |
| `server/src/index.ts` | `npm run dev` / `npm run start` 的入口，第一行调用 |
| `server/src/scripts/migrate.ts` | 迁移脚本会打印中文（版本号、数据表） |
| `server/src/scripts/seed.ts` | 种子脚本会打印中文（初始化结果、图片目录） |

没有引入任何新依赖；`dist/` 构建产物会正常包含该 helper，Linux/macOS 上该函数是空操作。

### 8.4 两个关键实现细节（避免踩坑）

1. **不能给 `spawnSync` 加 `windowsHide: true`。** 该选项会给子进程创建独立隐藏控制台（`CREATE_NO_WINDOW`），`chcp` 只改到那个新控制台，父控制台仍是 936。实测加与不加的结果：加 → `after=936`；不加 → `after=65001`。
2. **没有改 npm 脚本（如 `"dev": "chcp 65001 && tsx watch src/index.ts"`）。** npm 在 Windows 走 cmd、在 POSIX 走 sh，`chcp` 只在 cmd 存在，写进脚本会直接破坏 macOS/Linux 下的启动。放在 Node 启动早期判断平台，既覆盖 dev/start/migrate/seed 四个入口，也不影响跨平台。

### 8.5 验证方式与结果

验证环境：Windows + PowerShell，先手动把当前控制台代码页设回 936 模拟用户默认环境，再从 `server/` 目录真实启动 `npm run dev`（用 3100/3101 端口，避免占用默认 3000）。

## 9. 问题修复记录

### 9.1 「开始制作」点击后接口返回 400

**现象**：商家看板 / 商家订单详情点「开始制作」，接口 `POST /merchant/orders/:id/start` 返回 400，页面提示「服务器内部错误」；但联调时同样的接口是通的。

**复现**：用临时库（`DB_FILE=./data/repro.db`）启动服务，按小程序端真实请求形态逐个变体调用，结果如下：

| 请求形态 | 结果 |
| --- | --- |
| `POST` + `content-type: application/json` + **无 body**（小程序实际形态） | **400** `FST_ERR_CTP_EMPTY_JSON_BODY` |
| `POST` + `content-type: application/json; charset=utf-8` + 无 body | **400** 同上 |
| `POST` + `content-type: application/json` + body 为空字符串 | **400** 同上 |
| `POST` + body `{}` | 200 |
| `POST` + 完全没有 content-type、没有 body（联调时 Node fetch 的形态） | 200 |

**根因**：小程序 [request.ts](file:///c:/projectCode/zhang-restaurant/miniprogram/api/request.ts#L96-L99) 给**所有**请求都加了 `content-type: application/json`（这也是 `wx.request` 的默认行为），而 `startOrder` / `completeOrder` / `cancelMerchantOrder` 这三个接口本身没有请求体。Fastify 内置 JSON 解析器遇到「声明 json 但 body 为空」会抛 `FST_ERR_CTP_EMPTY_JSON_BODY`（statusCode 400）；由于它不是业务 `AppError`，被 `setErrorHandler` 兜底成 `code: INTERNAL_ERROR / message: 服务器内部错误`，所以页面只能提示这句没有信息量的话。联调时脚本用 Node `fetch` 且没设 content-type，恰好绕过了这个分支，因此当时是通的。

**受影响接口**（同一根因，一并修掉）：

- `POST /merchant/orders/:id/start`（开始制作）
- `POST /merchant/orders/:id/complete`（完成）
- `DELETE /merchant/orders/:id`（商家取消）

**改在那一侧**：**后端**。[app.ts](file:///c:/projectCode/zhang-restaurant/server/src/app.ts#L29-L45) 替换 JSON content-type 解析器：空 body 解析为 `{}`，非空仍走 `JSON.parse`，解析失败返回 `VALIDATION_FAILED`「请求体不是合法的 JSON」。同时 [app.ts](file:///c:/projectCode/zhang-restaurant/server/src/app.ts#L91-L100) 把 `FST_ERR_CTP_*` 统一映射为 `VALIDATION_FAILED` + 可读文案，不再落到「服务器内部错误」。

为什么不在前端改成传 `data: {}`：`wx.request` 的默认 `content-type` 就是 `application/json`，光去掉显式 header 并不能避免；而给这几个本来就无参数的接口硬塞空对象是把协议问题挪到调用方，任何其他客户端（curl / 第三方）仍会踩同一个坑。后端把「空 JSON body」视为空对象是更稳的一层，同时保留了请求体 schema 校验能力。

**验证**（全部使用小程序的请求形态：`content-type: application/json` + 无 body）：

| 用例 | 期望 | 实测 |
| --- | --- | --- |
| 待处理 → 开始制作 | 200，status=cooking | 200 `{status:"cooking"}` |
| 制作中 → 完成 | 200，status=completed | 200 `{status:"completed"}` |
| 重复开始制作 | 409 `ORDER_STATE_INVALID` | 409「只有待处理的订单可以开始制作」 |
| 重复完成 | 409 `ORDER_STATE_INVALID` | 409「只有制作中的订单可以完成」 |
| 待处理直接完成（越级） | 409 | 409「只有制作中的订单可以完成」，`params.status=pending` |
| 无 token | 401 `AUTH_REQUIRED` | 401 |
| 非商家用户 | 403 `ROLE_FORBIDDEN` | 403「需要商家权限」 |
| 不存在的订单 | 404 `ORDER_NOT_FOUND` | 404 |
| 商家取消（DELETE + json 头 + 无 body） | 200 | 200 `{deleted:true}` |
| 取消后再取消 | 404 | 404 |
| `POST /orders` 空 body | 400 `VALIDATION_FAILED`，且提示缺 `items` | 400，`fields:[{field:"items",message:"must have required property 'items'"}]` |
| 非法 JSON（`{oops`） | 400 `VALIDATION_FAILED` | 400「请求体不是合法的 JSON」 |

状态机没有被放宽：`start` 仍只允许 `pending`、`complete` 仍只允许 `cooking`，越级与重复操作继续按 409 拒绝。

验证用的临时库与临时脚本已删除，`data/restaurant.db` 未受影响；`npm run build` 通过。前端无需改动（`miniprogram` 目录本次没有任何文件变更）。
