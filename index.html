01 / ARCHITECTURE

总体架构

小程序只发 HTTPS 请求；Caddy 负责 TLS、反向代理与图片静态读取；Fastify 单进程鉴权并调用业务模块；SQLite 与图片目录同机持久化。

请求走向与分层
单进程 + WAL · 不使用 WebSocket
请求边界小程序不直连数据库、不持有存储密钥；鉴权、角色校验与状态迁移都不在客户端。
订单隔离客户接口强制按 JWT 的 uid 过滤；商家接口不按用户过滤，返回全部订单。
数据与文件SQLite 和图片都放本机持久目录；不做多实例，不做自动备份体系。

核心关系

03 / EXECUTION FLOWS

六条关键流程

每条图只表达一条主路径；异常分支（权限不足、状态不允许、重复评价）在图中用红色标记。所有流程均与当前表结构一致。

01 · 客户点餐下单（含订单食材快照）
入口：菜单 → 购物车 → 提交
快照生成是下单事务的一部分；任一菜品已下架或事务失败，整单不落库。
02 · 商家推进订单：待处理 → 制作中 → 完成
入口：订单看板
整单只有一个进度，没有逐菜状态；客户与商家看到的是同一条时间线。
03 · 采购清单生成与查看
入口：商家 → 采购清单
同一食材被多道菜、多个订单需要时，只显示一条食材记录并标注涉及订单数。
04 · 客户评价：一单一评 + 菜品评分
入口：订单完成 → 去评价
商家只能隐藏评价内容，不能修改星级；菜品详情展示均分与条数。
05 · 超级用户授权商家权限
入口：超级用户 → 用户授权
角色不写进 JWT，授权与撤销都在下一次请求立即生效。
06 · 软删除取消订单
入口：待处理订单 → 取消
软删除保留追溯能力；采购快照不物理删除，只在下一次聚合时排除。

后续单独补充。当前不建推荐表、不做推荐接口、不在菜单页放推荐位。

  • 将来表：独立表 recommendation_event（user_id、dish_id、scene、score、reason、model_version、created_at）；可选给 dish 加可空列 ai_tags。均为加法，不迁移现有字段。

05 / CONSISTENCY NOTES

对齐说明与取舍

本轮把 方案设计.md 中“中英文已实现”的表述修正为“预留”，并补齐字段级模型与 DDL。以下为评审时需要留意的取舍。

本次对齐修订
  • 01中英文切换改为本期不实现：去掉 locale 接口参数与页面语言开关，保留 locale / name_en / intro_en 字段。
  • 02AI 推荐不进入现有表：本期不加字段、不加接口，将来以独立表 + 独立路由 + 菜单页条件区块追加。
  • 03订单保持三状态：取消用 deleted_at 软删除，不新增 cancelled 状态，不物理删除。
  • 04采购只查 order_ingredient 快照，按食材去重；无数量、单位、库存、成本。
  • 05所有图表与 docs/架构与数据模型.md 的 DDL 一致；DDL 已在内存 SQLite 中执行通过，10 张表、12 个显式索引。
评审注意事项
  • 01本期所有角色切换都不换账号，订单隔离依赖 customer_id。
  • 02cooking 与 completed 不可取消；异常走线下沟通。
  • 03首个登录用户自动成为超级用户，存在抢注风险，需确认部署顺序或改用初始化口令。
  • 04服务器与备案域名尚未确认；小程序合法域名必须 HTTPS 且备案。
  • 05不做自动备份；SQLite 单文件按需自行拷贝。
